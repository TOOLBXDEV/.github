Overview

This document describes how MQL, SQL and pipeline data moves from HubSpot into reports. It is a companion to Funnel Mechanics, which defines what each stage means and how contacts, accounts and deals are labelled.

This artifact covers three things Funnel Mechanics does not:

  • Data flow and cadence — source systems, processing steps, refresh timing and latency at each stage.
  • Reporting definitions — the exact counting rules, formulas, and exclusions used to produce numbers.
  • The Data Definition Library — a machine-readable configuration layer (not yet built) that will live in the Sales Hub and power every Claude-built dashboard.

For canonical definitions of MQL, MQA, SQL, HIRO, campaigns and labelling rules, see Funnel Mechanics.

mos_last_deliberate_action

This contact property tracks the timestamp of a contact's most recent deliberate action (calls, meetings, form submissions, etc.). It's set by two HubSpot workflows and is used to determine Engaged ICP Contact and Engaged ICP Account counts. A contact is "engaged" if mos_last_deliberate_action falls within the last 90 days.

Exclusions from reporting

Records flagged with exclude_from_reporting = true are excluded from all metric counts. This flag currently covers:

  • 385 legacy Marketplace deals (pre-platform era)
  • Pre-February 2025 closed deals
  • 33 manually flagged non-ICP deals
Open issue

The exclude_from_reporting flag is documented in the Growth RAG Board but not yet in Funnel Mechanics. A full audit of flagged records has not been completed.

Definitions for reporting

Rates & ratios

Rates compare metrics within the same funnel. A rate divides two same-unit metrics (e.g., deals ÷ deals). A ratio compares different units (e.g., deals ÷ contacts) and requires care in interpretation. See Funnel stages for how each stage feeds the next.

Rate / RatioFormulaTypeUnit
MQL → SQLSQL count ÷ MQL countRatiodeals / contacts
SQL → HIROHIRO count ÷ SQL countRatedeals / deals
HIRO → WonWon count ÷ HIRO countRatedeals / deals
SQL → WonWon count ÷ SQL countRatedeals / deals
MQL → WonWon count ÷ MQL countRatiodeals / contacts
MQA → SQLSQL count ÷ MQA countRatiodeals / companies

Rate (same-unit)

Both numerator and denominator count the same object type (deals). The result is a true conversion rate and can be read as a percentage.

Example: SQL → HIRO = 45% means 45% of SQLs reach Solution Review.

Ratio (cross-unit)

Numerator and denominator count different objects (deals vs contacts). The result indicates efficiency but is not a direct conversion rate.

Example: MQL → SQL = 22% means 22 deals per 100 MQL contacts — not that 22% of MQLs "converted."

Definitions for reporting

Sourced & influenced pipeline

Pipeline value is attributed to campaigns in three ways. See Deal attribution in Funnel Mechanics for the full rules on Primary deal source.

Attribution typeDefinitionField
Marketing-sourced Deal where Primary deal source is a Marketing-owned campaign. Full deal value credited. primary_deal_source → campaign with owning_function = Marketing
Sales-sourced Deal where Primary deal source is a Sales-owned campaign. Full deal value credited. primary_deal_source → campaign with owning_function = Sales
Influenced Deal where any associated contact has a campaign label, regardless of Primary deal source. Multi-touch, weighted. All associated campaign labels on deal contacts

Multi-touch weighting

Influenced pipeline uses a W-shape attribution model. Credit is distributed across three key touchpoints:

  • First touch (30%) — the campaign that first engaged the contact
  • MQL touch (30%) — the campaign that qualified the contact as MQL
  • Deal-creation touch (30%) — the campaign closest to deal creation
  • Remaining touches (10%) — split equally among all other campaign touches

Data Definition Library

The dashboard data layer

The Data Definition Library is a machine-readable configuration layer that will live in the Sales Hub and power every Claude-built dashboard. Where Funnel Mechanics is the human-readable "what and why," the Library is the machine-readable "how to query and display."

Dashboards like the Growth RAG Board consume library entries to know what to count, how to filter, what thresholds trigger RAG status, and how to format the output.

Today vs. future

Today (hardcoded)

The Growth RAG Board embeds data arrays and metric definitions directly in JavaScript. Adding a metric means editing HTML. Each dashboard is independent — no shared definitions.

const D = {
  mql: [14, 18, 22, ...],
  sql: [8, 12, 15, ...]
};
const METRICS = {
  mql: {name:"MQL", fmt:"n", data:D.mql}
};

Future (Library-driven)

Dashboards read metric definitions from the Library. Adding a metric means adding a Library entry. All dashboards share the same source of truth.

// Dashboard reads from Library
const metrics = await salesHub
  .getLibraryEntries({area: "marketing"});
// Each entry has: name, formula,
// filters, thresholds, format
// Dashboard renders automatically

Operations

Workflow dependencies

Workflows have ordering constraints. Running them out of order produces incorrect data.

ProcessDepends onMust complete before
Reconciler HubSpot activity data Attribution scan, MQL lifecycle update
Attribution scan Reconciler (labels must be current) Reports (primary source must be set)
Review queue Reconciler (produces held changes) Next reconciler run (approved changes in CRM)
MQL lifecycle Reconciler (mos_mql_date must be set) Reports (lifecycle must be current)
Write conflict risk

The reconciler and the attribution scan both write to contact and deal records. They must not run concurrently. The attribution scan is scheduled for 07:00 to avoid overlap with the reconciler, which runs during overnight hours.

Reporting lock

MQL and MQA dates set before 1 September 2026 are final and cannot be changed by any workflow. This prevents retroactive changes to historical reporting. See Dates in Funnel Mechanics.

Build plan

Open items

These are reporting-specific decisions and issues that need resolution. See also Open items in Funnel Mechanics for upstream issues.

exclude_from_reporting audit

The flag is used in the Growth RAG Board but is not documented in Funnel Mechanics. It covers 385 legacy Marketplace deals, pre-Feb-2025 closed deals, and 33 manually flagged non-ICP deals. A complete audit is needed to verify coverage and add the flag to Funnel Mechanics.

Owner: Revenue Operations

ARR field standardization

Three revenue fields exist in HubSpot: arr ($25k default), annual_recurring_revenue_w_est ($27k default), and hs_arr (native). The Library needs a single canonical ARR field for revenue metrics.

Owner: Revenue Operations · Decision needed before: Library schema finalization

MQL counting unit

The Growth RAG Board appears to count MQLs at the company level in some views but the canonical definition in Funnel Mechanics counts MQLs at the contact level. The Library must encode one counting rule per metric — which unit does each dashboard use?

Owner: Revenue Operations · Reference: MQL definition

RAG threshold definitions

The Growth RAG Board uses a vs-previous + vs-last-year comparison to determine green/amber/red status. Should the Library encode the same logic, or should thresholds be target-based (≥105% = green, ≥90% = amber, <90% = red)?

Owner: Revenue Operations + Data Engineering

Dashboard query layer architecture

How should the dashboard engine query HubSpot using Library definitions? Options: direct HubSpot API calls at render time, a cached intermediate data store, or pre-computed snapshots. Trade-offs: freshness vs. performance vs. complexity.

Owner: Data Engineering

Library serving mechanism

How should dashboards access Library configs? Options: Sales Hub MCP tool (consistent with existing architecture), static JSON config file, or a dedicated API endpoint. Each has different implications for caching, versioning and access control.

Owner: Data Engineering

Library governance

Who can add, modify, or retire Library entries? Changes to a Library entry change every downstream dashboard. Proposed: changes require RevOps Council review; entries reference Funnel Mechanics anchors so they stay aligned with canonical definitions.

Owner: Revenue Operations
